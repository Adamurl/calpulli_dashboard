# Presentation client email workflow

[Documentation index](../README.md) · [API](api.md) · [Templates](templates.md) · [Gmail provider](gmail-provider.md)

The detailed HTTP contracts are in the [email workflow API](api.md) and [template API](templates.md). The [Gmail provider reference](gmail-provider.md) covers the internal adapter interface. This guide covers policy and operation.

Email belongs to the existing presentations module. Existing inquiry states stay unchanged. `new`, `declined`, and `completed` recommend emails on creation or a real state change. The remaining milestones use explicit staff workflow events. In particular, `booked` alone does not prove a signed contract and received payment.

## Policy registry

`backend/app/modules/presentations/email_registry.py` is the typed policy registry.

| Event | Template | Sending policy |
| --- | --- | --- |
| inquiry_created | inquiry_received | Automatic |
| missing_information | more_information_needed | Approval required |
| approved_for_call | schedule_call | Approval required |
| call_booked | meeting_confirmation | Automatic |
| call_reminder_due | meeting_reminder | Automatic |
| call_completed | conversation_follow_up | Approval required |
| contract_ready | contract_and_payment | Approval required |
| signed_and_paid | booking_confirmed | Automatic |
| final_logistics_needed | final_logistics_request | Automatic |
| event_details_complete | final_confirmation | Approval required |
| presentation_completed | thank_you_feedback | Automatic |
| balance_overdue | payment_reminder | Approval required |
| inquiry_declined | decline_or_referral | Approval required |
| special_situation | custom_follow_up | Manual only |

Declines and custom follow-ups never dispatch automatically. Pricing changes, negotiation, contract exceptions, payment arrangements, and sensitive communications must use a manually prepared custom follow-up. Never route those communications through an automatic event. A custom follow-up requires staff editing, approval, and an explicit send action.

The `signed_and_paid` event requires both `contract_signed=true` and `payment_received=true`. These are staff attestations, not integrations with a signing or payment system. Call events require a timezone-aware `call_at`. Call date, time, and timezone come from that timestamp, not the event date. The reminder event is only eligible within 24 hours before the call.

## Temporary templates and staff page

The user authorized temporary reference copy because approved copy is not available yet. Migration 0004 seeds all thirteen required templates and a custom follow-up template from the versioned `backend/alembic/data/email_templates_v1.json`. These are examples, not approved organizational copy. Every template starts with `ready_for_use=false`; no reference template can send until staff review it and mark it ready.

Open `/staff/presentations/INQUIRY_UUID`. Enter a current Supabase user access token from an approved staff session. The page uses the existing protected API and keeps tokens in memory only. It shows the inquiry state, recommendation reason, messages, previews, recipients, approval status, missing variables, tasks, timeline, and template editor. All client data requires bearer authorization. The public HTML shell contains no inquiry data. Do not share user access tokens with clients.

Replace reference copy in the template editor and mark it ready. Named variables use brackets, such as `[Name]` or `[Booking Link]`. All requested variable names are supported. Unknown variables and missing required values fail validation. HTML is generated by escaping rendered plain text; staff cannot inject arbitrary HTML.

Existing drafts retain their copy. Use **Refresh from template** to adopt updated copy, or edit a draft and its variables. Editing always resets approval. Refreshing requires a new approval where the policy requires it. Refresh does not send email. Explicit send actions may send a complete automatic draft after template review. Templates do not retroactively send old inquiries.

The backend verifies individual Supabase users and requires membership in `STAFF_USER_IDS`. Existing persisted audit actors remain `internal-staff` or `system`; they do not yet carry the verified user ID. Do not treat these as per-person approvals. Fine-grained staff roles and individual audit attribution remain future work. A separate `EMAIL_SEND_AGAIN_TOKEN` grants the send-again capability. The panel only shows Send again after that token is verified. Send again prepares a new approval-required draft and does not bypass review.

## API

All paths below are under `/api/v1/presentations` and require a valid Supabase user JWT and staff approval.

| Method | Path | Behavior |
| --- | --- | --- |
| GET | `/email-templates` | List copy and readiness |
| PUT | `/email-templates/{key}` | Replace subject, body_text, ready_for_use |
| GET | `/email-capabilities` | Delivery mode and verified send-again capability |
| GET | `/{inquiry_id}/emails` | State, registry, recommendation, messages, open staff tasks |
| POST | `/{inquiry_id}/email-events` | Record an event, prepare once, dispatch eligible automatic emails |
| PATCH | `/{inquiry_id}/emails/{message_id}` | Edit variables, subject, body_text, recipient_email, optional reply_to_id |
| POST | `/{inquiry_id}/emails/{message_id}/refresh` | Re-render from current template |
| POST | `/{inquiry_id}/emails/{message_id}/approve` | Approve a complete draft |
| POST | `/{inquiry_id}/emails/{message_id}/send` | Explicit send |
| POST | `/{inquiry_id}/emails/{message_id}/cancel` | Cancel an unsent message |
| POST | `/{inquiry_id}/emails/{message_id}/retry` | Explicit bounded safe retry |
| POST | `/{inquiry_id}/emails/{message_id}/send-again` | Prepare a new draft; also requires `X-Email-Resend-Token` |

An event body has `event`, optional `variables`, and event-specific attestations/timestamps. For example:

```json
{
  "event": "approved_for_call",
  "variables": {"Booking Link": "https://example.org/book"}
}
```

Missing values create a staff task and blocked draft. Complete it through the draft editor. Retrying the same event returns its original email and does not overwrite staff edits. Unmatched states create no email. Historical imports do not trigger emails.

The existing activities endpoint includes email timeline entries through `email_message_id`, `actor_id`, and `summary`. Both `request_id` and the `inquiry_id` response alias identify the inquiry. Email records and tasks use `inquiry_id`; `presentation_id` points to the same existing presentation request because there is no separate booking/presentation entity.

## Delivery and idempotency

There is deliberately no background queue, worker, scheduler, polling loop, or automatic retry job. Page loads only read data and never call Gmail. Eligible automatic emails send synchronously after persistence during create/update/event requests. Those write requests can wait for Gmail. Provider calls have a 15-second timeout per request, including OAuth refresh. Follow-up dispatch for a blocked automatic draft uses an explicit send action.

The 24-hour reminder is an explicit event for now. Staff must record it at the appropriate time. Scheduled reminders and durable asynchronous delivery remain the deferred stretch goal.

The database enforces uniqueness on inquiry ID, template key, and triggering event. Senders lock the inquiry and re-read message state. The claim and `SENDING` timeline entry commit before network delivery. Repeated sends of a `SENT` message return that message without contacting Gmail. A send-again action creates a new event identity and requires approval.

Gmail does not provide a transactional idempotency key for send. A timeout, send 5xx, interrupted process, or crash between Gmail acceptance and database persistence can leave delivery uncertain. `SENDING` and uncertain failures block retries. Staff must reconcile the mailbox before any recovery; there is no unsafe automatic recovery endpoint. Rate limiting and failures known to precede message submission support explicit retries, at most three attempts total. Invalid recipients and permission failures require staff review. Errors use safe fixed messages, not Gmail response bodies.

## Gmail setup

Default settings are `EMAIL_PROVIDER=mock` and `EMAIL_TEST_MODE=true`. Tests force the mock provider regardless of provider selection. Mock delivery persists a simulated sent record with `mock-` provider IDs and never contacts Google.

Configure these through the existing server-only environment/settings pattern:

- `GOOGLE_CLIENT_ID`
- `GOOGLE_CLIENT_SECRET`
- `GOOGLE_REDIRECT_URI`
- `GOOGLE_REFRESH_TOKEN`
- `GMAIL_SENDER_EMAIL`
- `GMAIL_SENDER_NAME`
- `EMAIL_PROVIDER` (`mock` or `gmail`)
- `EMAIL_TEST_MODE`
- `EMAIL_TEST_RECIPIENT`
- `EMAIL_SEND_AGAIN_TOKEN` (optional separate staff capability)

Obtain a refresh token for the organizational sender with only `https://www.googleapis.com/auth/gmail.send`. Enable Gmail API and complete the OAuth consent/administrator review appropriate to that mailbox. OAuth consent and code exchange happen outside this first version; `GOOGLE_REDIRECT_URI` documents the URI used during that setup. The adapter refreshes the token and calls `users.messages.send` with a base64url MIME multipart message. It does not create Gmail drafts or request read/modify permissions.

When test mode is enabled, all outgoing mail redirects to `EMAIL_TEST_RECIPIENT`, with the original recipient in `X-Calpulli-Original-Recipient`. Missing test recipient blocks delivery. No client email address is logged. Redirected tests omit original client thread headers and IDs so the test recipient cannot join a real client conversation.

For replies, select a previously sent message from the same inquiry and recipient using `reply_to_id`. The application preserves its subject and passes Gmail threadId plus RFC Message-ID in In-Reply-To and References. Gmail IDs and RFC Message-IDs are distinct. Incoming reply ingestion is not implemented and requires additional scope/design review later.

## Production setup still required

Review and approve template copy, apply migration 0004 on the authorized target, configure organizational OAuth and sender, run a redirected Gmail smoke test, and explicitly choose live delivery only after review. Verify individual staff identity/permissions before exposing client data in production. Use the server database role with the required table access; new tables preserve RLS with no browser policies and revoke browser-role privileges.

Background delivery, scheduled reminders, automatic retry execution, reply ingestion, and uncertain-delivery reconciliation tooling are deferred.

## Local verification

Run the existing backend Ruff and pytest commands. `tests/test_email_workflow.py` uses isolated SQLite with a test-only JSONB compiler for service/API behavior; it does not establish PostgreSQL migration or locking correctness. Existing integration tests still require a dedicated PostgreSQL database ending in `_test`. Never point these at the application database.

The browser check uses fictional records and the mock provider. Start `python3 tests/browser/server.py` from `backend/`, then run `node tests/browser/email_workflow.mjs` in another terminal with Playwright and Chrome available. `PLAYWRIGHT_MODULE` may point to an existing Playwright module; no frontend package or runtime dependency is added. The browser database lives in a temporary directory. Stop the server after testing.
